# DingoFS 测试平台：第一版设计草案

状态：待审阅，尚未进入实施。日期：2026-09-21。

## 1. 已确认的目标

面向 DingoFS 组员，统一选择并执行 dingofs-integration-test 与 dtt 的测试用例、场景；选择已有测试环境；管理机器资源和已部署的 DingoFS 集群。

第一版测试默认复用现有集群。同时提供独立的集群部署、更新、启动、停止、重启和清理任务，均通过 dingo 执行。配置采用“常用参数表单＋高级 YAML 编辑”。提交测试不会隐式重新部署集群。

成功标准：组员无需登录测试机拼接命令，即可完成选用例、选环境、提交、查看进度和报告；管理员能明确管理集群和资源，所有任务可追溯。

## 2. 第一版范围与边界

包含：成员登录和权限、机器登记、导入集群、环境配置、测试目录同步、测试任务、集群运维任务、资源排队、日志、报告、操作历史。

第一版同一集群的测试串行；不同集群且不共享独占资源的任务可以并行。先部署一个 Worker，协议允许增加 Worker，无需每台被测机器安装平台 Agent。

不包含：物理机装机、复杂审批流、自动版本回滚、无人值守故障恢复、多租户计费。自动部署与测试串联流水线、定时任务、趋势对比后续设计。

## 3. 对象关系

- **机器**：主机地址、可选物理机标识、标签、硬件信息、SSH 用户及凭据引用、维护状态；支持人工登记和只读探测。
- **集群**：部署配置、目标版本、发现的组件实例、管理节点及 dingo 执行上下文。一个机器可以部署多个实例或参与多个集群。
- **环境**：关联集群、测试客户端和负载机器、指定文件系统、挂载参数、工具位置及测试框架配置。第一版一个环境关联一个主集群。
- **测试定义**：来自特定代码版本的稳定 ID、名称、模块、标签、参数、前置条件、资源要求、执行适配器和报告类型。
- **任务**：测试或运维的统一执行记录；包含子任务、步骤、不可变配置快照、资源预留、日志和产物。

环境引用机器和集群，不复制一份脱离资源管理的主机清单。多个环境引用同一集群时，调度能识别共享关系。外部存储、元数据依赖等标记为“共享依赖”或“平台管理”，不因为出现在拓扑中就允许清理。

## 4. 页面和主要流程

导航：总览、测试目录、测试任务、测试环境、集群管理、机器资源、报告、系统管理。

### 4.1 创建测试

1. 选择来源和代码版本，按模块/标签搜索并勾选测试。
2. 选择兼容的环境，展示集群状态和占用情况。
3. 填写参数；显示用例数、场景展开数、重复轮次和预计数据量。没有历史依据时不编造完成时间。
4. 预览执行清单、所需资源、代码版本、环境快照和结束处理方式。
5. 提交并排队。浏览器关闭不影响任务。

例如 AI Storage 小文件默认 19 组合，应明确展示“19 组合×3 轮”，而不是只显示一个场景名。若后端只能提供整体进度，页面标为整体运行中，不虚构用例级进度。

任务详情：状态时间线、当前步骤、选中的用例及结果、实时日志、配置快照、产物、取消和重跑。重跑默认复制原快照生成新任务；已失效版本或不存在的资源会在检查阶段报错。

### 4.2 集群列表和详情

列表展示名称、用途、管理节点、发现版本、健康状态、状态更新时间、运行任务和维护标记。

详情包含概览、节点/组件实例、部署配置、操作记录、日志。期望配置与实际探测结果分开显示；查询失败显示“状态未知”，不能解释为停止。读到的数据均带采集时间。

### 4.3 导入已有集群

选择管理节点、执行用户、dingo 路径和凭据 → 列出现有集群 → 选择导入对象 → 读取拓扑及实例 → 关联机器资产 → 确认管理边界。

同一真实集群通过多个入口导入时提示关联已有记录，避免重复管理。导入只读，不自动提交配置、升级或重启。

## 5. 表单与 YAML 共用配置草稿

两种视图编辑同一份草稿，不维护两个相互覆盖的配置版本。

### 常用表单

- 基本信息：集群名称、用途、标签、管理节点、执行用户、工具路径。
- 部署：组件角色、关联机器、实例数量、端口、部署/数据/日志目录。
- 版本：组件镜像或安装包引用，以及工具实际支持的版本字段。
- 连接：服务地址、SSH 凭据引用、共享依赖。
- 环境配置另有：文件系统、客户端、挂载路径、测试工具路径、常用负载参数。

字段依照实际 dingo 拓扑格式建立，不预先杜撰 YAML 键名。每个字段显示默认值、单位、用途和作用范围。

### 同步规则

- 表单只更新它管理的字段；高级字段、未知扩展字段和 YAML 注释尽量保留，不能在保存时静默丢失。
- YAML 编辑后先做安全解析、重复键检查、结构及语义校验，再同步表单。禁止执行 YAML 自定义对象标签。
- YAML 有语法错误时保留编辑内容并标记错误位置，禁止发布；切换表单不能用旧值覆盖未修复文本。
- 表单无法表达但合法的结构显示为“由高级配置管理”，可以继续在 YAML 编辑，不能假装表单已完整表达它。
- 凭据使用引用。已有 YAML 含明文秘密时，导入阶段提示迁移至凭据管理；展示和配置差异不回显秘密。
- 多人编辑使用修订号，冲突时展示差异，不能后保存的人静默覆盖前一个人的修改。

### 配置生命周期

草稿 → 校验通过 → 发布配置版本 → 运维计划引用该版本 → 执行应用 → 探测实际状态。

“保存草稿”和“发布配置版本”都不直接修改远端集群。配置应用作为独立运维任务，在资源锁内提交给 dingo；是否需要重启由计划明确说明。保留上一版配置便于比对，但不承诺仅恢复 YAML 就能回滚数据或软件版本。

## 6. dingo 接入依据和边界

已在本地 `/mnt/disk5/daigy/dingofs-testsuite-tool/dingo` 上只执行帮助命令核对，未操作集群。当前工具公开：

| 平台能力 | 已确认的命令族 | 设计限制 |
|---|---|---|
| 集群目录 | cluster ls / add / checkout / rm | rm 与 clean 分开，具体删除语义需适配器验证 |
| 集群状态 | cluster status | 支持 host/role/id 过滤；帮助未声明 JSON，不假设存在 |
| 拓扑配置 | config show / diff / commit TOPOLOGY | commit 是远端变更，仅由运维任务执行 |
| 部署 | cluster precheck / deploy | 正常流程不使用跳过检查的 insecure |
| 更新 | cluster upgrade | 支持 host/role/id；不能把 dingo -u 当作集群更新 |
| 启停 | cluster start / stop / restart | 具体可选参数需要逐项核对 |
| 清理 | cluster clean | 显式指定对象与 only 内容，禁用默认全量清理 |
| 主机配置 | hosts ls / show / commit | 平台资产与工具主机清单建立关联，不盲目互相覆盖 |

**执行上下文是第一版的关键约束。** deploy 等命令针对当前集群，没有统一的显式 cluster 参数。绑定管理节点、OS 用户、dingo 配置目录和工具路径形成上下文。同一上下文的 checkout、配置读取、运维命令、状态查询必须串行，并在执行前后核对实际目标集群。

不能仅锁集群：两个不同集群若共用同一 dingo 当前集群上下文，仍会相互干扰。支持隔离配置目录后可以使用独立上下文；未经验证前不假定工具支持该能力。

平台之外人工同时调用同一上下文仍存在竞争。第一版建议使用专用管理账号/上下文；无法隔离时，提供“人工维护”入口暂停平台任务，并要求人工操作遵守同一维护约定。

工具能力按版本探测。适配器保存原始输出、版本和解析器版本；不支持的功能在 UI 禁用并解释原因。状态解析失败不能返回空实例列表作为成功。

## 7. 运维操作与清理

流程：选择操作和范围 → 生成配置差异/实例清单/执行步骤 → 校验 → 获取资源锁后再次检查目标和状态 → 执行 → 健康检查 → 记录结果。

更新与部署明确目标组件制品和更新顺序。未验证工具具有滚动更新能力时，不在 UI 承诺无中断更新。升级 dingo 工具本身单独管理，不混在集群版本更新里。

清理分成三个不同入口：测试运行数据、组件日志/部署产物、集群持久数据。持久数据清理须展示明确实例及目录、输入集群名称确认；不可清理平台不管理的共享依赖。确认绑定计划摘要，计划变化后原确认失效。

测试数据只清理该任务登记的目录；平台不根据用户随意填写的路径执行递归删除。默认不展示直接删除目录的 no-recycle 高级选项。

普通成员可浏览、创建测试、取消自己的任务；管理员可管理资源和集群运维。运维取消只在已验证安全的步骤边界进行；中断命令不等于撤销操作。

## 8. 任务执行与资源调度

前端 → API → 持久化任务/调度器 → Worker → 测试适配器或 dingo 适配器 → 现有测试环境。

第一版采用一个持久化调度源，不同时引入互相独立的任务队列和资源状态。任务、配置修订、步骤、资源预留保存在数据库；日志和报告存储在独立产物目录。前端通过可续传的事件流获取日志，刷新页面从已知偏移恢复。

任务状态：草稿、排队、检查中、运行中、停止中、通过、失败、取消、待人工检查。基础设施执行错误和测试断言失败在结果中分开。

资源锁覆盖集群、实际机器/冲突域、dingo 上下文。第一版保守串行，共享物理机上的性能或破坏性任务不并行。记录排队原因，不让用户猜测为何不能启动。

Worker 持续上报心跳和任务进度。心跳过期时标记执行结果未知并隔离资源，不能立即重派同一部署、清理或测试操作；恢复后先核对实际进程、步骤和集群状态。平台重启不自动重跑非幂等命令。

每个任务保存代码 commit、工具/镜像版本、配置快照、计划摘要和实际命令。命令以参数数组生成，不把用户输入拼接成 Shell。测试取消追踪进程组/容器以及必要的远端清理；Worker 退出不能直接视为集群恢复。

## 9. 测试框架适配

两个项目输出机器可读测试目录。第一版可以分别增加只读的目录导出入口；目录同步不能调用测试 setup 或连接集群。目录与具体代码版本绑定。

选择稳定测试 ID，适配器转换为执行清单。多个 YAML 选择如果现有入口不能一次表达，就创建顺序子任务。共享初始化如何复用由适配器明确，不能每个子用例重新部署环境。

dtt 场景提供参数 schema 和展开计划，包括组合数、数据量、重复轮次。暂不支持目录解析的工具场景标记未接入，不能显示为已可运行。长期运行、故障注入和特殊资源需求需要显式标签。

报告保留：集成测试 Allure 原始结果/静态报告；dtt 原始日志、结构化结果和性能报告。平台按适配器的结果合同汇总，避免仅看 shell 返回码就把零用例执行判为通过。

报告页面隔离展示生成的 HTML，不让报告脚本获得平台登录凭据。凭据不进入命令展示、日志和可下载配置。

## 10. 第一版验收用例

1. 导入已有集群后可以查看实例及配置，期间没有远端变更。
2. 表单修改不丢失高级 YAML 字段；非法 YAML 和并发编辑冲突能明确提示。
3. 勾选多个集成用例和一个 dtt 参数场景后，执行内容与预览完全一致。
4. 同集群测试与重启任务不能同时执行；共享管理上下文的两个集群也不会串错目标。
5. 两个互不冲突环境可以并行，页面分别展示进度和日志。
6. 浏览器关闭、API 重启不终止运行中测试，也不重复执行运维步骤。
7. Worker 断联后资源进入待检查状态，未确认前不能自动重用。
8. clean 操作必须指定清理内容，普通成员无法调用；确认后计划变化会要求重新确认。
9. 失败任务能区分测试失败、环境检查失败、工具错误和未知远端结果。
10. 重跑保留原任务及参数快照，报告可以追溯实际代码与组件版本。

## 11. 后续实施顺序建议

先只读资产/集群导入与配置编辑；再实现任务和资源调度；接入集成测试和 dtt；最后逐项开放通过验证的 dingo 运维操作。第一版验收以本节之前的完整范围为准，不以“能从网页发起一个命令”作为完成。

实现前需通过本地探测补全各 dingo 子命令的输出及退出码、实际拓扑 schema、交互提示行为和执行上下文隔离能力；这些是适配器验证项，不能要求用户手工猜参数。登录优先采用团队已有身份系统，若暂无则使用平台本地账号，具体部署时确定。
